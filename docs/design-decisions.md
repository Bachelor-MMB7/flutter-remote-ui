| 2026-06-26 | **Flow logic lives in the client** (`_currentStep`); the server stays a generic file server, not a workflow engine like pyck — this defines the client↔server responsibility split (architecture A vs C)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Core of "Fetch-Once" (A): the client decides step order → no per-step roundtrip, and the workflow stays usable **offline** (the flow runs without the server; pyck's server-driven flow freezes offline). In C the server owns the schema and the flow and validates on submit, so the button does not gate client-side                                                                                                                                                                                                                                                                             | Server-side validation on submit (C) — not possible in A without a per-step roundtrip |
| 2026-06-28 | **In A the server sends only the UI definition, no backend data**. The `.rfwtxt` carries the UI — including *static* text/labels (headings, supplier address, product name). "Static" = authored in the template, identical for every case, and **not produced or changed by the client/user** (yet still server-editable → no app release). It carries no *per-instance backend* values — server-known or server-computed state the client cannot derive on its own (current stock, the ordered quantity of this PO, an order-number → product lookup). Every per-instance value instead comes from **user input** (typed order number, counted quantity, photo, picked location), held client-side in `data.workflow`. Deliberate choice (server = plain file server), **not an RFW limit** — RFW can carry data via `DynamicContent`, and C/pyck does   | A is fetch-once with no per-instance data channel. Test: *"could the client know this without asking the backend?"* — No → backend value → A cannot show it; Yes → user input → A shows it. Static template text is fine: identical for every case, and server-editable without a release                                                                                                                                                                                                                                                           | Hard-coding or faking server-side per-instance values (ordered quantity, current stock, a live lookup) in the template; or treating "no backend data" as an RFW limitation rather than our design choice |
| 2026-06-28 | **Capability is fixed in the binary; composition is dynamic**: local widgets are the vocabulary shipped in the app, and the server recomposes them → new or restructured screens ship without an app release; only a genuinely new capability needs a release                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | The SDUI advantage is not component reuse (native apps reuse too) but server-side recomposition without a release — restructuring the screen flow took no client-code change                                                                                                                                                                                                                                                                                                                                                                        | Calling "reuse" the SDUI advantage; shipping every layout / flow change as an app release |
| 2026-06-28 | **Offline reach: A runs a full workflow without the server; C does not** A's bundled `default.rfwtxt` is a *complete, self-contained workflow* (all steps + client-side flow + client-held data) → the app loads and runs end-to-end offline, even on a first launch with the server down. In C the bundled default is only a library of templates; the workflow itself — which step, the order, the per-instance data — comes from the server. So C's default only fills in when the remote UI is missing **but server data still flows**; with no server there is no workflow at all | A keeps flow + data in the client and fetches only the UI definition (cached/bundled) → the server is needed only for UI *updates* → offline-resilient. C keeps flow + per-instance data + step transitions on the server → the UI templates alone render nothing                                                                                                                                                                                                                                                                                   | Treating pyck's bundled default as an offline workflow (it is template-only); or claiming A's offline reach without noting it rests on flow + data being client-side |
| 2026-06-30 | **ETag / conditional-GET caching deferred to future work** — removed from the server for now; the client always fetches the full `.rfw`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | App start has two steps: (1) fetch the file, (2) build the screen. ETag only helps step (1), and barely: the `.rfw` is a few KB and the client still makes the round-trip to ask "changed?", so over LAN the saving is ~0. Step (2) — decode + build — is identical whether the bytes come from the network or from disk, and step (2) is exactly what RQ3 measures, which ETag does not speed up. A generic HTTP optimisation, orthogonal to A-vs-C and to the render metric                                                                       | Building it now for marginal transport savings (no thesis value); stale-while-revalidate / cache-first render — a larger, separate design, also parked as future work |
| 2026-07-02 | **Deployment time is timed on the phone only** — start when the phone asks for the new `.rfw`, stop when the new screen shows. No timestamp taken on the server                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Two devices (server & app) have two clocks that are never set exactly the same (this offset is called **skew**). Starting on the server clock and stopping on the phone clock would mix the two, so the skew ends up in the measured time. Timing both moments on **one** clock (the phone) avoids that. The trip to the server and back is still counted, because it happens **between** the two phone timestamps                                                                                                                                              | Starting the clock on the server (would only fit if the server actively pushed updates — ours instead waits for the phone to ask) |
| 2026-07-02 | **The time to create the file and upload it to the server is not measured.** Native is not stopwatched either — its number is the **App-Store review time**, taken from Apple/Google docs                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | How the file gets onto the server (by hand, `flyctl`, GitHub Actions) is **different in every company** and is the **same work for native apps too** — so it says nothing about the architecture. Both sides therefore start from the same point: *change is finished and handed off*. Review time is even a fair, conservative number for native — a native change also needs every user to update the app afterwards, which SDUI does not                                                                                                         | Measuring the upload; treating CI / GitHub Actions as part of the result |
| 2026-07-02 | **Measurement server is kept warm** — the fly.io machine runs continuously (`min_machines_running = 1` for the measurement runs, reverted to `0` afterwards once the apps were no longer in use) and as a single machine during RQ2 runs                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | RQ2 measures the full fetch time. A sleeping machine adds its start-up time to the first request, so some trials would be slow (cold) and others fast (warm). Keeping one machine always on lets every trial start from the same state, and using only one machine means every request goes to the same server, so it can never land on a second one that is still cold | Scale-to-zero (auto-stop) + a warm-up request before each run — saves resources but relies on remembering to warm up; a missed warm-up leaks a cold outlier |
| 2026-07-08 | **SO3 span split into wait (tap → build start) and render (build start → first frame): render time is the comparison metric, total tap→frame is kept for the 100 ms threshold**                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | The wait share is display-raster lottery (0–16.7 ms, set by where the tap lands in the frame period) — identical mechanism in both apps, but phase-locked by the test driver, which made rfw *look* faster in the raw median. The render share (build incl. RFW interpretation + layout + paint) is the only part where the architectures actually differ, so the RFW overhead is read there. The total span is still reported because the 100 ms perceptibility threshold is defined from the tap, not from build start. **Trade-off:** reporting both costs extra instrumentation (a second clock read at build start) and an explanation of why the wait share does not count for the comparison | Comparing raw tap→frame medians only (contains the rhythm artifact → wrong winner); reporting render time only (loses the operator-facing 100 ms check, which needs the full tap→frame span) |
| 2026-07-04 | **Static template literals stay in the template — never moved into `DynamicContent`** (e.g. product name / SKU appear as literals in ProductDetail *and* SummaryRow, not stored once in `data.workflow.product` and bound)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | `DynamicContent` is written only by the **client**, and the client is **tenant-agnostic** — it knows the interaction *categories* (quantity, photoPath, orderNumber, location), not tenant content like "Washers". A value enters the state only when a **user action** carries it (typed, counted, picked — a template-authored location string still counts as user input because the *choice* is the user's act). "Product" has no user action, so binding it would force tenant content into `_pushWorkflowData` → per-tenant client code → app release — exactly the cycle SO1 removes | Storing template literals in `DynamicContent` to avoid repetition (DRY) — saves a duplicate string but breaks the generic client and fakes a data flow that A does not have |
