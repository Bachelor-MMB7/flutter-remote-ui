# RFW Client Design Decisions

> App-specific decisions for `apps/rfw-client`.
> Cross-cutting decisions (affecting **both** client and server) live in [`/docs/design-decisions.md`](../../../docs/design-decisions.md).

---

| Date | What | Why | Rejected |
| ---- | ---- | --- | -------- |
| 2026-06-23 | Client structure follows the official RFW "remote" example ([example/remote/lib/main.dart](https://github.com/flutter/packages/blob/main/packages/rfw/example/remote/lib/main.dart)) | Proven reference pattern (Runtime, DynamicContent, RemoteWidget); fewer own mistakes when starting with RFW | Build the RFW setup from scratch without a reference |
| 2026-06-24 | Scanner screen = **photo capture** (not barcode); the photo flows back as a **file-path string** via `DynamicContent` and is shown in the summary; a new local `ImagePreview` widget renders `Image.file(path)` | Testable without a physical code, and it demonstrates the **RFW rendering boundary** — RFW cannot render an image, so the native capability stays in a local widget while the server only places the trigger | Barcode/QR scan — needs a physical code to test and gives a weaker "RFW boundary" story (just another string round-trip) |
| 2026-06-24 | **Tenant-switch lever** in the client (switch tenant at runtime → re-fetch the workflow) | Demonstrates multi-tenancy (one app, per-tenant server-driven UI); smallest feature with the biggest demo value | Hard-coded single tenant in `_loadFromServer` |
| 2026-06-24 | **Client caching + offline fallback (built)** = three levels: (1) server reachable → save the fetched `.rfw` to one device file, (2) server unreachable → render that cached file, (3) no cache yet → render a default UI shipped inside the app | Cache and fallback are one mechanism; the bundled default guarantees the app always renders something, even on a first launch with no server and no cache | In-memory only (lost on restart); or no bundled default (first offline launch shows nothing) |
| 2026-06-26 | Bundled default UI as **text** `.rfwtxt` (parsed with `parseLibraryFile`), not binary `.rfw` (`decodeLibraryBlob`) | The default is hand-maintained in the repo → text is readable and diffable in git; binary stays for the over-the-wire path where size/speed matter | Ship the default as a binary `.rfw` blob |
| 2026-06-25 | **One `.rfw` per workflow** (e.g. `order.rfw`), not one bundled file for the whole app | Conscious scope boundary; bundling kept as future work | Bundle all workflows into a single file || 2026-06-26 | **Generic, workflow-agnostic data namespace** `data.workflow.X` (was `data.order.X`); client always pushes to `_data.update('workflow', …)` | The client is a generic runner and should not hard-code one workflow's name in the data path; one namespace serves every workflow and reinforces the "generic client" story | Per-workflow namespace (`data.order`, `data.goods-receipt`) coupling the data path to each workflow name |
| 2026-06-27 | **Styling stays in the local widgets** (color, icon, padding are fixed per widget); the server only chooses *which* widget + *what* data + the flow, not how it looks | The local widgets are the app's design system → consistent look across tenants, branding stays in code/review, and the `.rfwtxt` definitions stay lean | Expose every style as an `.rfwtxt` parameter → server controls the full look, but risks visual inconsistency and bloated definitions |
| 2026-06-28 | **Local widgets form three tiers**: (1) basic / structural — `InfoBox`, `Space`, `ActivityContainer`, `ActivityHeader`; (2) generic & reusable — `SelectableOption`, `ConfirmButton`, `TextInput`, `QuantityStepper` (parameterised, reused across screens and tenants); (3) tenant / domain-specific — `ProductDetail`, `PhotoButton`, `ImagePreview` (used once per tenant, for one specific step) | Mirrors pyck's mix of generic primitives plus concrete domain components; the reusable parts stay generic, while a specific step can still get a purpose-built widget | Forcing every widget to be generic; or making everything domain-specific |
| 2026-06-28 | **Generic required-field gate on `ConfirmButton`** (`require` + `requiredValue`), pointed at one data field per screen, instead of the fields being hard-coded in the widget | The server points the same generic rule at any field per screen, so the button stays reusable | Field-coupled gate (`requireSelection` + fixed `orderNumber` / `location`) baked into the widget |
